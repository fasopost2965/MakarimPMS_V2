## CH-028 — Composants UI manquants : tabs, file-upload, diff-viewer

- **Titre** : Compléter `components/ui/` avec les primitives manquantes
- **Source** : `docs/audits/PHASE_11_FRONTEND_QUALITE.md` §8
- **Description factuelle** : `frontend/src/components/ui/` ne contient que 6 primitives (`badge`, `button`, `dialog`, `input`, `label`, `select`). Trois catégories de manques identifiées :
  1. **Tabs** : `StockPage` émule des onglets via `useState` + boutons classés manuellement — aucun composant `Tabs` partagé
  2. **File-upload** : `DocumentOcrPage` utilise un `<input type="file">` natif non stylé sans zone de dépôt
  3. **Diff-viewer** : `AuditPage` affiche les diffs `oldValue`/`newValue` via `<pre>{JSON.stringify(changes, null, 2)}</pre>` brut, illisible pour un responsable non technique
- **Modules concernés** : frontend transverse (`components/ui/`), `features/stock`, `features/document-ocr`, `features/audit`
- **Priorité** : Important · **Criticité** : Modérée
- **Impact métier** : Modéré (UX dégradée sur 3 écrans) · **Impact sécurité** : Aucun · **Impact conformité** : Aucun · **Impact exploitation** : Modéré
- **Dépendances** : CH-029 (DataTable) et CH-030 (Toast) dépendent de l'ouverture de ce chantier
- **Livrable attendu** :
  - `components/ui/tabs.tsx` : composant `<Tabs>` / `<TabsList>` / `<TabsTrigger>` / `<TabsContent>` (pattern shadcn/ui ou équivalent accessible — attributs `role="tablist"` / `role="tab"` / `role="tabpanel"`, `aria-selected`, `aria-controls`)
  - `components/ui/file-upload.tsx` : zone de dépôt drag-and-drop avec preview du nom de fichier, fallback `<input type="file">` accessible
  - `components/ui/diff-viewer.tsx` : affichage côte-à-côte (ou inline) des champs `oldValue`/`newValue` avec coloration syntaxique JSON minimale (lignes ajoutées en vert, supprimées en rouge)
  - Intégration dans les 3 pages concernées (`StockPage`, `DocumentOcrPage`, `AuditPage`)
- **Critères de validation** :
  1. `StockPage` utilise `<Tabs>` avec navigation clavier fonctionnelle (Tab + flèches)
  2. `DocumentOcrPage` affiche une zone de dépôt avec retour visuel au survol/dépôt
  3. `AuditPage` affiche un diff lisible sans `JSON.stringify` brut
- **Statut** : **à faire**
- **Estimation** : 2–3 jours · **Confiance** : élevée
- **Lien audit** : Phase 11 §8

## CH-031 — ErrorBoundary global

- **Titre** : Empêcher qu'une exception de rendu dans un onglet fasse tomber toute l'application
- **Source** : `docs/audits/PHASE_11_FRONTEND_QUALITE.md` §5
- **Description factuelle** : `grep -r "ErrorBoundary" frontend/src/ → 0 résultat`. Une exception JavaScript lancée pendant le rendu d'un composant React provoque un **écran blanc complet** — toute l'app disparaît, pas seulement l'onglet fautif. C'était le point 1 du Lot 0 du plan d'origine, jamais livré.
- **Modules concernés** : frontend transverse (`App.tsx`)
- **Priorité** : P0 · **Criticité** : Critique
- **Impact métier** : Élevé (perte totale d'accès pendant un incident) · **Impact sécurité** : Aucun · **Impact conformité** : Aucun · **Impact exploitation** : Critique (un bug dans un onglet secondaire fait tomber la réception entière)
- **Dépendances** : aucune
- **Livrable attendu** :
  - `components/ErrorBoundary.tsx` : composant React class `ErrorBoundary` avec `componentDidCatch` (console.error) et un fallback UI (`<div role="alert">`) affichant un message d'erreur friendly + bouton « Recharger la page »
  - Wrapping de chaque onglet dans `App.tsx` : `<ErrorBoundary key={activeTab}><ActiveFeature /></ErrorBoundary>` — `key={activeTab}` force le reset de la boundary au changement d'onglet
  - Optionnel mais recommandé : un wrapping global supplémentaire autour de `<Router>`/`<AppShell>` pour capturer les erreurs hors-rendu
- **Critères de validation** :
  1. Lancer `throw new Error('test')` dans le rendu d'un onglet → seul cet onglet affiche le fallback, les autres onglets restent fonctionnels
  2. Cliquer « Recharger la page » restaure l'onglet à son état initial
  3. `console.error` journalise bien l'exception (preuve que `componentDidCatch` est appelé)
- **Statut** : **à faire**
- **Estimation** : 2h · **Confiance** : élevée
- **Lien audit** : Phase 11 §5

## CH-034 — Tokens JWT → cookies httpOnly

- **Titre** : Éliminer l'exposition des tokens JWT en `localStorage` (risque XSS)
- **Source** : `docs/audits/PHASE_11_FRONTEND_QUALITE.md` §3 ; `docs/governance/REGISTRE_DECISIONS.md` RD-016
- **Description factuelle** : `frontend/src/lib/token-storage.ts` stocke `accessToken` et `refreshToken` en clair dans `localStorage`. Une injection XSS peut exfiltrer les deux jetons, y compris le refresh qui donne une session persistante volée. Signalé comme RD-016 dans le registre des décisions — jamais résolu.
- **Modules concernés** : `frontend/src/lib/token-storage.ts`, `frontend/src/lib/api-client.ts`, backend `auth` (nouveau endpoint de refresh par cookie)
- **Priorité** : P0 · **Criticité** : Critique
- **Impact métier** : Faible direct · **Impact sécurité** : Critique · **Impact conformité** : Élevé (RGPD/protection de session) · **Impact exploitation** : Faible (transparent pour l'utilisateur si bien implémenté)
- **Dépendances** : aucune technique bloquante, mais coordination backend + frontend nécessaire
- **Livrable attendu** :
  - Backend : `AuthController.login()` et `AuthController.refresh()` émettent le `refreshToken` dans un cookie `httpOnly; Secure; SameSite=Strict; Path=/auth/refresh` via `response.cookie()` (NestJS) — plus jamais dans le corps de la réponse
  - Backend : nouvelle route `POST /auth/refresh` acceptant le cookie (sans corps JSON)
  - Frontend : `token-storage.ts` ne stocke plus que l'`accessToken` en mémoire (variable de module) — suppression de tout appel à `localStorage`
  - Frontend : `api-client.ts` adapté pour le cycle accessToken en mémoire + refresh par cookie automatique sur 401
  - Tests e2e backend : vérifier que `Set-Cookie` est bien émis à la connexion et que `POST /auth/refresh` sans cookie échoue (401)
- **Critères de validation** :
  1. Après login : `localStorage` ne contient aucune clé contenant `token`, `jwt` ou `access`
  2. Le refresh token n'apparaît jamais dans un corps de réponse JSON
  3. Un refresh réussi ne nécessite aucune interaction utilisateur
- **Statut** : **à faire** (référencé RD-016, décision de migration confirmée)
- **Estimation** : ~1 sprint (3–5 jours, coordination backend + frontend) · **Confiance** : élevée
- **Lien audit** : Phase 11 §3 ; RD-016

## CH-036 — Tests frontend Vitest + Testing Library
